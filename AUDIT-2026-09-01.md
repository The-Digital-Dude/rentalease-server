# RentalEase Production Audit — 1 September 2026

**Scope:** Render production logs `04:27–06:23 UTC`, plus code audit of `rentalease-server` and `rentalease-app`.
**Trigger:** Minimum Safety Standard (MSS) job completions failing; server restart observed.

---

## Executive summary

The headline problem is real and reproducible from the logs: **large Minimum Safety Standard submissions do not complete, the technician retries, and the duplicated work exhausts the server until Render restarts it.**

One MSS submission succeeded and one failed in the same session. The difference is payload size, and the failure mode is a cascade, not a single bug:

| | Succeeded 04:27 | Failed 06:18 |
|---|---|---|
| Job | `6a9610ea…402d` | `6a960708…36eb` |
| Files | 36 | **81** |
| Format | all JPEG | **mostly HEIC** |
| Approx. payload | ~7 MB | **~105 MB** |
| Media upload | 26 s | never finished |
| PDF generation | 21 s (7.4 MB) | never reached |
| **Total** | **71 s** | **aborted ×2, then restart** |

The 71-second success is the important number: it is already past the point where the mobile client gives up. Every MSS job larger than that one is expected to fail the same way.

A second, separate defect was reported during the audit and is confirmed: **reports save successfully but jobs are never marked Completed** (C0). Same underlying shape — a multi-step flow with no server-side linkage between the steps. Around 25–30 jobs are currently affected.

**Severity counts:** 4 Critical · 4 High · 3 Medium · 3 Low

---

## Critical

### C0 — Reports save but jobs are never marked Completed

**Reported symptom:** "most of the reports got submitted, the reports are on the server, but the jobs don't get completed." Confirmed, with a known cause and an unused fix already present in the codebase.

Job completion is a **second, separate HTTP request** that the mobile app fires only after the report upload returns:

```
04:28:42  POST  /api/v1/inspections/jobs/…       201   ← report saved
04:28:49  PATCH /api/v1/jobs/6a9610ea…/complete  200   ← job completed
```

Report submission ([inspectionReport.service.js:1149](src/services/inspectionReport.service.js#L1149)) saves the report and links it to the job but never touches the status:

```js
job.reportFile = pdfUpload.url;
job.latestInspectionReport = report._id;
job.inspectionReports.push(report._id);
await job.save();          // ← status is still "Due"/"Scheduled"
```

`job.status = "Completed"` is written in exactly one place — `finalizeJobCompletion` ([job.routes.js:685](src/routes/job.routes.js#L685)) — reachable only via that `PATCH`. Anything interrupting the gap between the two calls leaves **report saved, job incomplete**: a client timeout (C3), the app backgrounded or killed during a 71-second upload, a dropped connection, or the technician closing the modal.

Corroborating evidence: report submission emails the completed-job report only `if (job.status === "Completed")`, which is never true at that point on a first submission. That branch has been dead code throughout — itself a sign the two steps were assumed to be one.

**The trap in the obvious fix.** Setting `status = "Completed"` during report submission would silently break invoicing, because `finalizeJobCompletion` opens with:

```js
if (job.status === "Completed") {
  return buildCompletedJobSuccessResponse(job, {...});   // early return
}
```

The follow-up `PATCH` would short-circuit here and skip invoice creation and `JOB_COMPLETED` notifications — trading a visible bug for an invisible revenue one.

**The fix already exists and is not being used.** The server has a complete three-stage resumable submission flow:

| Endpoint | Purpose |
|---|---|
| `POST /jobs/:id/inspection-submissions` | Creates a submission record keyed by `clientSubmissionId` (idempotent) |
| `POST /jobs/inspection-submissions/:id/media-batch` | Uploads media **in batches**, deduped against `existingMediaUploads` |
| `POST /jobs/inspection-submissions/:id/finalize` | Submits the report **and** calls `finalizeJobCompletion` in one atomic, idempotent step ([job.routes.js:3224](src/routes/job.routes.js#L3224)) |

The mobile app uses none of them — it still uses the legacy two-call flow. Migrating the client fixes **both** critical findings at once:

- `finalize` performs report submission and job completion together, and caches its `completionResponse`, so a retry is safe and a job can no longer be left orphaned.
- Batched media upload removes the single 105 MB request that causes C1, which structurally resolves the memory pressure behind H1 and H2.

This flow also stores `lastError` and a `ready_to_finalize` status, so an interrupted submission can be resumed rather than restarted.

### C1 — MSS submissions abort and take the server down with them

**Evidence (verbatim from logs):**

```
06:18:47  [Inspection Submit] Uploading inspection media files { filesCount: 81 }
06:21:34  POST /api/v1/inspections/jobs/6a960708e5eb1addb6bc36eb - - ms - -
06:23:18  POST /api/v1/inspections/jobs/6a960708e5eb1addb6bc36eb - - ms - -
06:23:32  ==> Running 'node index.js'
```

The same pattern appears earlier for a different job:

```
05:12:04  POST /api/v1/inspections/jobs/6a961285e5eb1addb6bc41c5 - - ms - -
05:13:04  POST /api/v1/inspections/jobs/6a961285e5eb1addb6bc41c5 - - ms - -
```

`- - ms - -` means Express never wrote a response — the connection was torn down mid-flight. The `==> Running 'node index.js'` line is Render restarting a process that died; nothing in the application logged a shutdown, which is the signature of an **OOM kill**, not a handled crash.

**Why it happens — the full chain:**

1. 81 files, mostly HEIC at 1–4 MB each, are uploaded to disk by multer.
2. `uploadInspectionMedia` ([inspectionReport.service.js:808](src/services/inspectionReport.service.js#L808)) processes them **strictly sequentially** — a nested `for…of` over field groups then files, with `await` on HEIC decode, sharp compression, and GCS upload for each one.
3. Elapsed time blows past the mobile client's socket timeout.
4. The technician sees a hang, taps **Complete Job** again.
5. The server has **no in-flight guard**, so request 2 begins the entire 81-file pipeline from scratch while request 1 is still running.
6. Two (then three) concurrent pipelines, each holding decoded image buffers, exceed the container's memory. Render kills the process.

Each of steps 3, 5 and 6 is independently fixable; they are listed separately below as C2, C3 and H1.

**Confirmed against the 512 MB instance.** The numbers leave no room for a second pipeline:

| Component | Peak |
|---|---|
| Node + Express + Mongoose baseline | ~120 MB |
| sharp decoding one 4032×3024 HEIC to raw RGBA | **~49 MB** |
| `prepareRenderableMedia` retained buffers (81 × ~250 KB) | ~20 MB |
| PDF buffer + `Buffer.concat` doubling | ~34 MB |
| **One pipeline** | **~223 MB** — survivable |
| **Two concurrent pipelines** | **~326 MB** + heap fragmentation → **over 512 MB** |

A single 81-photo submission fits, with little margin. The moment the technician's retry starts a second one, the container is past its limit — which is exactly the sequence in the log. This also explains why the 36-file submission at 04:27 succeeded despite the same code path: one pipeline, smaller images, no retry.

A related contributor: Node was started with no `--max-old-space-size`, so V8 sized its heap from the *host's* memory rather than the 512 MB cgroup limit and never ran an aggressive GC before the kernel killed the process. Fixed in the changes below.

### C2 — No concurrent-submit guard on inspection submission

There is no idempotency key, no lock, and no in-flight registry for `POST /api/v1/inspections/jobs/:jobId`. I searched for all of them:

```bash
grep -rn "inFlight|submitLock|idempot|activeSubmi|processingJobs" \
  src/services/inspectionReport.service.js src/routes/inspection.routes.js
# → only an unrelated `new Set()` at line 460
```

There *is* a per-file duplicate guard using `clientMediaId` ([inspectionReport.service.js:851](src/services/inspectionReport.service.js#L851)), but it compares against **media already persisted**. While request 1 is still in flight nothing is persisted yet, so request 2 sees an empty set and redoes every upload. The guard only protects against a retry *after* a completed run — precisely the case that does not need protecting.

**Fix:** hold a per-job in-flight lock (module-level `Map` is sufficient for a single instance; Redis or a Mongo `findOneAndUpdate` sentinel if you ever run more than one). Return `409 Conflict` with a "submission already processing" message on the second request rather than starting a second pipeline.

---

### C3 — Mobile client sets no upload timeout and surfaces no progress

[services/jobs.ts:585](../rentalease-app/services/jobs.ts#L585) issues a bare `fetch` with no `AbortController`, no timeout, and no upload-progress reporting:

```js
const res = await fetch(`${baseUrl}/api/v1/inspections/jobs/${jobId}`, {
  method: "POST",
  headers: { Authorization: `Bearer ${token}` },
  body: formData,
});
```

Consequences:

- The platform default socket timeout applies. On iOS that is **60 s** — shorter than the 71 s that a *successful* MSS submit already takes.
- With no progress indicator, a working upload is indistinguishable from a frozen one, which is what drives the manual retries in C1.
- There is no client-side retry logic, so the duplicate requests in the logs are the technician tapping the button again. Any fix must therefore be visible in the UI, not just in the network layer.

**Fix:** raise the timeout well above worst-case (or disable it and rely on a server response), show real upload progress, and disable the submit button while a request is outstanding.

## High

### H1 — Peak memory scales linearly with photo count in two places

**a. All prepared images are held simultaneously.**
`prepareRenderableMedia` ([inspectionReportPdf.service.js:5455](src/services/inspectionReportPdf.service.js#L5455)) downsamples each photo to 1200 px and pushes it into a `preparedItems` array that is not released until the PDF is finished. The in-code comment claims this "prevents OOM" — it reduces the constant, but the growth is still `O(n)`: ~81 × 250 KB ≈ 20 MB of retained buffers, on top of sharp's working set for whichever image is being decoded.

**b. The finished PDF is doubled in memory.**

```js
doc.on("data", (chunk) => chunks.push(chunk));
doc.on("end", () => resolve(Buffer.concat(chunks)));
```

`Buffer.concat` allocates a second contiguous copy while the chunk array is still live. The 36-photo report produced a 7.4 MB buffer; 81 photos extrapolates to ~17 MB, so ~34 MB at the concat spike — then the whole buffer is held again for the GCS upload.

**Fix:** stream the PDF directly to GCS instead of buffering, and release each image buffer once it has been drawn rather than retaining the full array.

### H2 — Identical photos are uploaded and processed multiple times

The technician attached the same source images to several sections. From the 06:18 payload:

- `IMG_7690.heic` (1.7 MB) — window-coverings, window-covering-anchors, bathroom-facilities → **×3**
- `IMG_7685`, `IMG_7682`, `IMG_7673`, `IMG_7656`, `IMG_7655`, `IMG_7634`, `IMG_7633`, `IMG_7667`, `IMG_7666`, `IMG_7665`, `IMG_7663`, `IMG_7693`, `IMG_7694`, `IMG_7704`, `IMG_7705`, `IMG_7669`, `IMG_7686`, `IMG_7687` — **×2 each**

That is roughly **20 redundant files (~25 MB)** transferred, HEIC-decoded, compressed, and uploaded to GCS — then decoded and downsampled *again* during PDF generation. Deduplicating by content hash would cut this submission's work by around a quarter for no behavioural change.

### H3 — Auth tokens written to logs in plaintext

[property.routes.js:343](src/routes/property.routes.js#L343):

```js
console.log("🔍 Token verification debug:");
console.log("Token:", token);
```

Verification tokens are printed in full to Render's log stream, which is retained and readable by anyone with dashboard access. This is leftover debugging, not deliberate instrumentation.

**Fix:** delete it, or log only a short prefix behind a debug flag.

### H4 — No HTTP server timeouts configured

[src/server/index.js:32](src/server/index.js#L32) creates the server and calls `listen` without setting `requestTimeout`, `headersTimeout`, or `keepAliveTimeout`. Node's default `requestTimeout` of 5 minutes means an abandoned 100 MB upload keeps its socket, its temp files, and its handlers alive long after the client is gone — which is exactly what the two aborted POSTs did while a third pipeline was starting.

## Medium

### M1 — PDF generation timeout does not stop the work

[inspectionReport.service.js:1107](src/services/inspectionReport.service.js#L1107) races PDF generation against a 5-minute timer:

```js
const PDF_GENERATION_TIMEOUT = 5 * 60 * 1000;
const pdfBuffer = await Promise.race([ buildInspectionReportPdf({...}), ... ]);
```

`Promise.race` only decides which result is *observed*. The losing promise keeps running, keeps its buffers, and keeps consuming CPU — so on timeout you pay the full cost anyway and simply stop waiting for it. Under the C1 cascade this makes memory pressure worse, not better.

**Fix:** make the PDF builder cancellable (an `AbortSignal` checked between sections) so the timeout actually reclaims the work.

### M2 — Duplicate Mongoose schema indexes

Every boot logs seven warnings:

```
Duplicate schema index on {"email":1} … {"trackingKey":1} … {"quotationNumber":1} …
Duplicate schema index on {"sessionId":1} … {"callSid":1} …
```

Cause: fields declared `unique: true` *and* re-declared via `schema.index()`. Confirmed pairs include [Technician.js:25,35](src/models/Technician.js#L25) with [:531](src/models/Technician.js#L531), [Agency.js:21,35,45](src/models/Agency.js#L21) with [:340](src/models/Agency.js#L340), and [Quotation.js:12](src/models/Quotation.js#L12) with [:192](src/models/Quotation.js#L192).

Harmless at runtime, but it is seven lines of noise on every boot that will mask a real index warning when one appears. Remove the redundant `schema.index()` calls.

### M3 — Deprecated MongoDB driver options

`useNewUrlParser` and `useUnifiedTopology` are passed on every connection and have had no effect since driver v4. They warn on each boot and will break when the option is removed. Delete both.

## Fixes applied

The three changes that break the cascade are implemented and syntax/type-checked:

| # | Change | File |
|---|---|---|
| **C2** | Per-job in-flight lock; a concurrent submit is rejected with `409 INSPECTION_SUBMISSION_IN_PROGRESS` instead of starting a second pipeline. Released in a `finally` so a crash cannot wedge the job. | [inspection.routes.js:243](src/routes/inspection.routes.js#L243) |
| **C3a** | `AbortController` with a 10-minute timeout replaces the 60 s platform default; `409` is surfaced as a clear "already submitting" message. | [jobs.ts:585](../rentalease-app/services/jobs.ts#L585) |
| **C3b** | Re-entrancy guard at the top of `handleSubmit` — the button was disabled, but the confirmation flow could still call it twice. | [JobCompletionModal.tsx:1485](../rentalease-app/components/JobCompletionModal.tsx#L1485) |
| **H4** | `requestTimeout` 15 min (allows slow large uploads), `headersTimeout` 65 s and `keepAliveTimeout` 61 s (abandoned sockets released promptly). | [src/server/index.js:32](src/server/index.js#L32) |
| **OOM** | `--max-old-space-size=384` so V8 sizes its heap to the 512 MB container instead of the host, and GCs before the kernel kills it. | [package.json:10](package.json#L10) |

Together these stop the outage at both ends: the client no longer gives up on a healthy upload, and if a retry does happen the server refuses it rather than doubling its memory use.

### Reconciliation for the 25–30 orphaned jobs (C0)

`POST /api/v1/jobs/admin/reconcile-incomplete-reports` — SuperUser only, added at [job.routes.js:3011](src/routes/job.routes.js#L3011).

Finds jobs with `latestInspectionReport` set and `status !== "Completed"`, and completes them through the normal `finalizeJobCompletion` path so behaviour matches a real completion exactly. `completedAt` is backdated to the report's own `submittedAt`, so the record reflects when the technician actually finished rather than when reconciliation ran.

**Dry run is the default.** It reports what it would do and changes nothing:

```bash
curl -X POST https://<host>/api/v1/jobs/admin/reconcile-incomplete-reports \
  -H "Authorization: Bearer <superuser-token>" -H "Content-Type: application/json" -d '{}'
```

Add `{"apply": true}` to actually complete them. Failures are captured per job, so one bad record cannot halt the run.

**Blast radius, verified in code before building this:**

| Side effect | Status |
|---|---|
| Technician payments | `TECHNICIAN_PAYMENTS_ENABLED = false` — skipped |
| Auto invoice/document delivery to PMs & agencies | `AUTOMATED_COMPLETED_JOB_DOCUMENTS_ENABLED = false` — skipped |
| Draft invoice creation | **Happens for every compliance job**, regardless of `hasInvoice` — see below |
| `JOB_COMPLETED` notifications | **Will fire** — ~3 per job (SuperUsers + assigned technician) |

**Correction.** An earlier version of this document stated that no invoices would be created because `hasInvoice` is opt-in. That is wrong for compliance jobs. [job.routes.js:587](src/routes/job.routes.js#L587) creates a draft invoice from agency pricing for every `jobCategory === "compliance"` job; the `hasInvoice === "true"` path is the `else if` branch and applies only to non-compliance jobs:

```js
if (job.jobCategory === "compliance") {
  // …always creates a Draft invoice from agency pricing
} else if (hasInvoice === "true" && invoiceData) {
```

The invoices are created with `status: "Draft"` and, with `AUTOMATED_COMPLETED_JOB_DOCUMENTS_ENABLED = false`, are not emailed to agencies or property managers. So they are internal draft records rather than client-facing bills — but they are created, and the earlier claim that none would be was incorrect.

A side effect: completion **fails** for any compliance job whose agency has no pricing configured for that job type, since the invoice cannot be built. Those jobs need agency pricing set before they can be reconciled.

So expect roughly **70–90 internal emails** to staff and technicians, a draft invoice per compliance job, and no client-facing mail. Run the dry run first and check the list.

## Still outstanding

Ordered by value:

1. **C0 client migration** — move the mobile app onto the existing `inspection-submissions` flow. This is the real fix for both C0 and C1, and it makes H1/H2 largely moot by removing the single oversized request. *Biggest win by a wide margin.*
2. **H3** — remove the plaintext token logging. *One-line change, do it with the next deploy.*
3. **H2** — deduplicate media by content hash (~25 MB of redundant work in the failing submission). Less urgent once batching lands.
4. **H1** — stream the PDF to GCS, release image buffers after drawing.
5. **M1** — make PDF generation genuinely cancellable so the 5-minute timeout reclaims work.
6. **M2, M3, L1** — boot-noise and dead-code cleanup, batchable into one commit.

## Deployment note

The server changes need a **manual Render deploy** (auto-deploy is off by request). The mobile changes need an **OTA push**. Deploy the server first: the client's new `409` handling expects the lock to exist, and shipping the client alone would leave the retry path unguarded.
